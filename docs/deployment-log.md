# 实际部署记录：我们做了什么，怎么做的

记录范围：2026-09-15 至 2026-09-17。以下内容由本机部署脚本、构建记录、证书信息与验证结果整理；为便于公开分享，设备名称、实际 IP、在线隧道地址和凭据已替换为描述或示例。

## 1. 确认目录与部署方式

最初要求装在 D 盘，随后明确改为 E 盘。本机实际只有 C、E 盘，因此最终使用 `E:\MinIO`。为避免引入额外虚拟化环境，没有安装 Docker 或 WSL。

查询 MinIO 官方仓库后确认源码发行状态。普通 Git 拉取遇到网络连接重置，于是改用 Go 模块方式获取固定源码并编译：版本 `v0.0.0-20251015172955-9e49d5e7a648`，源码提交 `9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a`。Go 模块校验保持启用。

Go 压缩包经 SHA-256 核验后解压到 E 盘。引导 Go 为 1.27.1，实际构建选择 Go 1.24.8，设置 `CGO_ENABLED=0`、`-p 4`、`-trimpath` 和发行版本标记。`TEMP`、`TMP`、`GOTMPDIR`、`GOPATH`、`GOMODCACHE`、`GOCACHE`、`GOBIN` 都重定向到 E 盘，`GOENV=off`。

产出的 MinIO 可执行文件约 108 MiB，初期连同工具和缓存共约 2.71 GiB。构建缓存保留在 E 盘，未把“清理缓存”记作已完成。Windows 本身、浏览器和系统级组件仍可能使用 C 盘，不能承诺 C 盘零写入。

## 2. 配置账户、运行脚本和登录自启动

使用 Windows DPAPI 将 `PSCredential` 加密保存为 `config\credentials.xml`，启动时才导入到 MinIO 环境变量。配置目录权限限制为当前用户、SYSTEM 和本机管理员。加密文件依赖原 Windows 用户和设备环境，不能简单复制给别的用户使用。

创建启动、停止、状态检查脚本，日志写入 `E:\MinIO\logs`，数据写入 `E:\MinIO\data`。用户随后自行修改了账户和密码，并完成重启。公开教程不记录真实凭据。

建立名为 `MinIO-Local-E` 的计划任务，触发条件是**当前用户登录**，以该用户权限运行启动脚本，测试返回值为 0。这不是“未登录也运行”的 Windows 服务。

最初服务通过本机 HTTP 验证：健康检查、管理页登录、S3 建桶/上传/列举/下载，以及重启后的 SHA-256 一致性；测试对象与临时桶随后删除。

## 3. 解释四个连接参数并检查网络

确认用户已有 `test` 桶，检查时桶内为空。说明 `Bucket` 是桶名，`Endpoint` 是 S3 地址，另外两个字段是一对访问凭据。管理页面 `9001` 不能作为 S3 Endpoint。

检查过本机内网 IP、网关、出口公网 IPv4、IPv6 和现有远程组网工具。出口公网 IPv4不等于能接收入站连接，且未发现可直接使用的公网 IPv6。现有 Tailscale 未登录，未把它配置为最终方案。

需求进一步明确：第三方程序强制 HTTPS，且用户无法管理路由器，也无法在对方服务器安装软件。因此，单纯使用内网 IP、路由器端口转发或双端 VPN 都不能直接满足当前条件。

## 4. 改为 MinIO 原生 HTTPS

选择 MinIO 自带 TLS，没有另外安装 Nginx 或 Caddy。生成 RSA 3072 位的本地根 CA 和服务端证书：CA 有效期约 10 年，服务端约 1 年。本次服务端证书在 2027-09-17 到期，准确时间以本机证书为准。

证书 SAN 包含 `localhost`、设备名称、`127.0.0.1`、`::1` 和当时的实际内网 IP。证书与私钥存放在 `certs`，公用 CA 证书放在 `client-certs`；CA 私钥仅在本机受保护目录保存。CA 导入当前 Windows 用户的受信任根证书存储。

S3 监听 `0.0.0.0:9000`，管理页面监听 `127.0.0.1:9001`。内网访问仍依赖操作系统防火墙、网络隔离策略和客户端证书信任。检查时本机防火墙已有关闭的配置；本次没有关闭防火墙，也没有新增放行规则，教程提供的是按需、小范围放行方法。

处理过两类问题：生成证书时目标子目录缺失，以及 Windows Schannel 检查私有证书吊销信息失败。最终通过补齐目录、核验证书签名、明确指定 CA 和 `--ssl-revoke-best-effort` 解决；未以跳过 TLS 验证作为方案。仓库证书脚本先创建全部目录，并拒绝覆盖已有材料。

HTTPS 下重新验证：证书链和 IP、健康接口、控制台登录、S3 完整读写，以及服务重启后的数据一致性。也验证了 Windows 当前用户默认根证书信任。

## 5. 用出站隧道解决跨网络访问

下载官方 cloudflared 2026.9.1，完成 SHA-256 校验；下载慢时使用分段重试，最终仍按官方摘要核验完整文件。工具和临时下载块均留在 E 盘。

确认可访问 Cloudflare 出站 TCP 7844，启动 Quick Tunnel：

```powershell
E:\MinIO\tunnel\cloudflared.exe tunnel --no-autoupdate --protocol http2 --edge-ip-version 4 --url https://127.0.0.1:9000 --origin-server-name localhost --origin-ca-pool E:\MinIO\client-certs\minio-root-ca.crt
```

Cloudflare 分配 `https://……trycloudflare.com` 临时地址。外部访问使用公共受信任证书，cloudflared 访问本机 MinIO 时使用自建 CA 验证源站证书。TLS 在 Cloudflare 终止后再转发，这不是对 Cloudflare 不可见的单一端到端加密连接。

保持请求 Host，不添加 `--http-host-header localhost`，以免影响 S3 Signature V4 校验。没有暴露 `9001` 管理页面，没有配置路由器入站转发，也没有在第三方服务器安装组件。

保存隧道启动、停止和查看 Endpoint 的脚本。隧道状态文件仅在本机记录当前地址。临时隧道没有加入自启动，因为重建后地址可能变化，第三方配置需要同步更新。

## 6. 验证公共 HTTPS + S3

从本机请求实际公共域名，通过公共证书验证，健康接口返回 HTTP 200。随后通过 S3 Signature V4 完成 `test` 桶列举、唯一测试对象上传、逐字节下载比较和删除。

这证明了“本机请求 → Cloudflare 公共入口 → 隧道 → MinIO”的实际链路。没有声称在另一台物理设备或用户最终的第三方平台上完成验收，也没有声称验证过大文件和长期在线稳定性。
